# Automatic Telegram Player ID validation

The intended customer flow is: enter a Player ID once, let the signed Windows Companion perform one read-only KemerBet **Find**, and save the ID automatically only when KemerBet returns that exact ID and the empty ETB transfer form. Finding an ID does not prove that the Telegram payer owns it. Several Telegram accounts may use the same Player ID; each Telegram account has one selected ID at a time.

The existing selected ID stays active during a new lookup. A newer request supersedes an older one. If the Companion is signed out, offline, receives an unexpected response, or cannot verify the empty form, the request remains inconclusive; no Player is approved or rejected from a network error. No lookup may fill an amount or click Transfer.

The request table, single-ID local Find, domain-separated signed assignment/result contract, Companion-side protected-key result signer, authenticated bridge handler, private one-use SQL state, and atomic selection function are **dormant foundation only**. The production bridge explicitly returns `503 temporarily_unavailable` on both Player-validation routes. The SQL functions are not granted to the bridge runtime. They do not connect Telegram requests to the Companion or make a Player eligible until explicitly wired. The contract binds one exact Player ID and request to a paired certificate, a five-minute one-use assignment, and either an exact-ID/empty-ETB-form observation or an inconclusive result. It cannot encode an amount, note, Transfer, or payment authority. An accepted `found` result records evidence only; a separate guarded finalization would create or reuse a shared beneficiary and switch the selected ID atomically. A prior explicit eligibility revocation remains review-required.

Before enabling this flow, a follow-up release must wire the reviewed private SQL calls to the bridge with exact role/preflight grants, complete the signed polling schedule around live financial work, trigger finalization after accepted evidence, and notify the bot requester of success or a safe retry/review state. That release needs additional cross-request concurrency and live-routine-idle tests. It must not turn on any payment switch as part of Player validation.
