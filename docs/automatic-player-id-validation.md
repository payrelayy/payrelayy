# Automatic Telegram Player ID validation

The intended customer flow is: enter a Player ID once, let the signed Windows Companion perform one read-only KemerBet **Find**, and save the ID automatically only when KemerBet returns that exact ID and the empty ETB transfer form. Finding an ID does not prove that the Telegram payer owns it. Several Telegram accounts may use the same Player ID; each Telegram account has one selected ID at a time.

The existing selected ID stays active during a new lookup. A newer request supersedes an older one. If the Companion is signed out, offline, receives an unexpected response, or cannot verify the empty form, the request remains inconclusive; no Player is approved or rejected from a network error. No lookup may fill an amount or click Transfer.

The request table, single-ID local Find, domain-separated signed assignment/result contract, Companion-side protected-key result signer, authenticated bridge handler, private one-use SQL state, and atomic selection function are **code-only foundation, not an activated customer flow**. The bridge routes and four exact private SQL functions were already wired and granted in the repository before this change; earlier text saying they always returned `503` was stale. Whether those migrations and services are installed in production must be checked separately. The contract binds one exact Player ID and request to a paired certificate, a five-minute one-use assignment, and either an exact-ID/empty-ETB-form observation or an inconclusive result. It cannot encode an amount, note, Transfer, or payment authority.

The private database boundary replaces direct evidence acceptance with an atomic accept-and-finalize call. An accepted `found` result either creates/reuses the shared beneficiary and selects that ID, or records a review-required decision in the same transaction. An inconclusive Find stays review-required and cannot select. A prior explicit eligibility revocation remains review-required. The bridge receives only the wrapper permission, never direct finalizer permission.

The bot has a durable, bot-only notification path for the latest signed terminal Find: `selected` or `review_required`. It never calls a pending request approved or a network failure an invalid ID. The queue stores no raw Player ID and starts with a **null cutover**; merely installing this migration or polling it sends nothing. A later guarded activation must set a fresh cutover only after the Find scheduler and full bot/API release are ready, and must exclude earlier test requests. An ambiguous Telegram send acknowledgement can repeat a message, never repeat the Player selection or initiate money movement.

The Windows Companion has a default-off routine-queue hook: after an empty financial lease, it may await exactly one signed read-only Player Find before claiming another deposit. It skips Find during a credit, reconciliation, outage, or signed-out session. The protected Automatic Deposits launcher still rejects an ambient internal flag; only an explicit `-EnablePlayerIdFind` launch switch maps to the read-only hook, and it cannot be combined with check-only or no-money preflight. Ordinary launches keep Find off. The standalone no-money Find mode remains separate.

The bot also has a default-off `INTERNAL_TELEGRAM_PLAYER_VALIDATION_INTAKE_ENABLED` switch. When explicitly enabled with its private action channel, a Player ID sent in reply to the bot's Set/Change Player ID prompt requests a signed Find instead of the existing immediate save; the existing selected ID remains in place until an exact signed result is accepted. A whole private text message containing exactly eight ASCII digits also requests that Find without requiring a prompt reply, before payment-reference handling. SMS text, receipt text, and numbers embedded in longer messages remain payment input. The old manual-review menu button is hidden. A callback from an earlier menu opens the new prompt rather than starting manual review. The production compose file enables this switch for the reviewed activation release; staging remains pinned off. Merely merging the change does not affect the running bot.

The disposable SQL suite now exercises competing requests in separate Postgres sessions and runs signed selection and review results through the bot notifier to a mock Telegram sender. Those tests must pass in CI before rollout; a local TypeScript build alone does not establish database behavior. Before deploying the production bot with intake enabled, the operator must verify the paired signed Companion is running with the read-only Find switch, the API/bridge and private migrations match the release, no older validation request is pending, and the notification cutover is set to a fresh timestamp excluding earlier tests. The cutover must precede the bot restart so a new request cannot be selected without a result notification. A guarded deployment and a separate activation decision are required. Player validation must not turn on any payment switch.
