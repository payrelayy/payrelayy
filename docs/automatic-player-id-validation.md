# Automatic Telegram Player ID validation

The intended customer flow is: enter a Player ID once, let the signed Windows Companion perform one read-only KemerBet **Find**, and save the ID automatically only when KemerBet returns that exact ID and the empty ETB transfer form. Finding an ID does not prove that the Telegram payer owns it. Several Telegram accounts may use the same Player ID; each Telegram account has one selected ID at a time.

The existing selected ID stays active during a new lookup. A newer request supersedes an older one. If the Companion is signed out, offline, receives an unexpected response, or cannot verify the empty form, the request remains inconclusive; no Player is approved or rejected from a network error. No lookup may fill an amount or click Transfer.

The request table and single-ID local Find in this change are **dormant foundation only**. They do not connect Telegram requests to the Companion or make a Player eligible. Before enabling this flow, a follow-up release must bind each queued request to a fresh server-signed single-ID assignment, authenticate the paired device's result, record immutable validation evidence, create or reuse a canonical beneficiary without assigning ownership to the first payer, and atomically change the saved ID only if the request is still current. The bot must then notify the requester of success or a safe retry/review state. That release needs disposable SQL integration, signed-protocol, replay, concurrency, and live-routine-idle tests. It must not turn on any payment switch as part of Player validation.
