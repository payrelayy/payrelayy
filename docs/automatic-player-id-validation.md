# Automatic Telegram Player ID validation

The intended customer flow is: enter a Player ID once, let the signed Windows Companion perform one read-only KemerBet **Find**, and save the ID automatically only when KemerBet returns that exact ID and the empty ETB transfer form. Finding an ID does not prove that the Telegram payer owns it. Several Telegram accounts may use the same Player ID; each Telegram account has one selected ID at a time.

The existing selected ID stays active during a new lookup. A newer request supersedes an older one. If the Companion is signed out, offline, receives an unexpected response, or cannot verify the empty form, the request remains inconclusive; no Player is approved or rejected from a network error. No lookup may fill an amount or click Transfer.

The request table, single-ID local Find, domain-separated signed assignment/result contract, Companion-side protected-key result signer, authenticated bridge handler, private one-use SQL state, and atomic selection function are **code-only foundation, not an activated customer flow**. The bridge routes and four exact private SQL functions were already wired and granted in the repository before this change; earlier text saying they always returned `503` was stale. Whether those migrations and services are installed in production must be checked separately. The contract binds one exact Player ID and request to a paired certificate, a five-minute one-use assignment, and either an exact-ID/empty-ETB-form observation or an inconclusive result. It cannot encode an amount, note, Transfer, or payment authority.

The next private database boundary replaces direct evidence acceptance with an atomic accept-and-finalize call. An accepted `found` result either creates/reuses the shared beneficiary and selects that ID, or records a review-required decision in the same transaction. An inconclusive Find stays review-required and cannot select. A prior explicit eligibility revocation remains review-required. The bridge receives only the wrapper permission, never direct finalizer permission. The bot still needs a separate durable result-notification path before this should be activated for customers.

The Windows Companion now has a default-off routine-queue hook: after an empty financial lease, it may await exactly one signed read-only Player Find before claiming another deposit. It skips Find during a credit, reconciliation, outage, or signed-out session. The protected Automatic Deposits launcher rejects the new internal flag and does not enable this hook, so routine Player validation remains off. The standalone no-money Find mode remains separate.

Before enabling this flow, a follow-up release must expose a guarded opt-in for the idle-only schedule and notify the bot requester of success or a safe retry/review state. It also needs cross-request concurrency and end-to-end notification tests, a guarded deployment, and a separate activation decision. Player validation must not turn on any payment switch.
