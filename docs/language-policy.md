# FetanAgent language policy

## Version 1 product language

FetanAgent is English-only in version 1. This applies to every FetanAgent-created, user-visible
artifact:

- responsive web/PWA account, sign-in, workspace, validation, recovery, notification, offline, and
  support messages;
- neutral team-workspace pages and any optional Telegram messages;
- website and API documentation intended for people;
- downloadable plans, guides, invoices generated by FetanAgent, PDFs, and other exported files;
- support templates, release notes, and help content.

Do not add a language selector, a per-user locale preference, or an Amharic copy of product text
in version 1. The shared locale contract is fixed to `en`.

## Canonical product vocabulary

The same generic public sign-in leads to the neutral `Workspace`. Customer-facing URLs, page titles,
navigation, errors, notifications, and help content must not expose the internal terms `Owner`,
`Admin`, `Owner Control`, `manual verification`, `job`, `lease`, `shadow`, or `payment claim`.
Shared staff capability routing through that generic entry remains a future server-side boundary;
neutral vocabulary must not be mistaken for implemented staff access.

Use these plain-English terms:

| Internal or legacy term | Customer-facing term                                                  |
| ----------------------- | --------------------------------------------------------------------- |
| Owner/Admin             | FetanAgent team                                                       |
| Owner/Admin dashboard   | Workspace                                                             |
| manual verification     | Being checked                                                         |
| pending validation      | Checking                                                              |
| Player-ID registration  | Add a Player ID                                                       |
| found / not found       | No direct existence status; use the final ownership-association state |
| provider evidence       | Payment information                                                   |
| payment claim           | Payment decision                                                      |
| job, lease, shadow      | Check, or omit when no customer term is needed                        |

The neutral team workspace may use `Review required`, `Source result`, `Decision`, `Reason`,
`Waiting for approval`, and `Approved by 1 of 2`. Exact role names, procedure names, workflow states,
and reason codes remain valid inside authorization, database, source-code, and audit boundaries;
the language policy does not rename technical identifiers.

Product copy must not imply that an existence check proves Player-ID ownership, that a human review
is automated, or that a submitted payment is confirmed. The customer Player-ID surface uses exactly
`Checking`, `Ready`, and `Could not confirm`. `Ready` is unreachable for a web-origin request because
web ownership association remains rejected. Any later implementation that can project `Ready` must
require both proof-bearing ownership and a separate current financial-eligibility decision; the
present list SQL does not join that ledger. Payment and withdrawal flows may additionally use
`Submitted`, `Confirmed`, `Expired`, and `Cancelled` only when their exact meaning is established by
the authoritative workflow.

## Data and evidence are not interface translations

This policy does not change user-provided or provider-provided data. Names, bank/payment evidence,
SMS text, screenshots, and PDFs may legitimately contain Amharic or another language. They remain
evidence or identity data and must not be translated, overwritten, or rejected merely because of
their language. Payment verification still requires authoritative provider evidence rather than
text translation or OCR alone.

## Future artifacts

There are currently no tracked FetanAgent PDFs, Word documents, spreadsheets, slide decks, or
other downloadable documents. When one is created, its FetanAgent-written content must be English
and it must be checked before delivery. Supporting a new product language later requires an
explicit product decision, updated copy, tests, and a reviewed data migration if a locale field is
introduced.
