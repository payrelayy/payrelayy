# Companion execution contracts v2

This private workspace package defines a **dormant, unprovisioned protocol contract** for a possible future Windows companion financial-execution lane. It does not enable deposits and is not imported by an application or runtime.

The package deliberately separates five signed artifacts:

1. `SignedExecutionEnrollment` binds a currently valid, server-signed v1 no-money device certificate to exactly one `platform_agent_account_id`, one pilot configuration, exact 2500-minor-unit ETB limits, and a separately trusted execution signer.
2. `SignedExecutionAssignment` binds an activation epoch and exact intent, job, attempt, account, pilot reservation, Player digest, enrollment, amount, and server validity window. An assignment is not permission to act.
3. `SignedOneUseActionAuthority` repeats every assignment binding and proves a named first-acquired database fence, request nonce, and very short validity window. Its signed deadline can never exceed either the assignment expiry or ten seconds after the database fence. This is the only signed schema that can participate in one-use action authority.
4. `SignedExecutionResult` is signed by the enrolled device and reports only `submission_attempted`, `local_uncertain`, `post_fence_no_local_action`, or `refused_before_fence`. Any started action must bind the authority and carry a distinct `finalActionStartedAt` strictly inside the fence/authority deadline; the later `reportedAt` alone receives the bounded reporting allowance. `post_fence_no_local_action` binds the consumed fence while stating only that this device did not locally start the action. It is reconciliation evidence, never a refusal, cancellation, or retry signal.
5. `SignedAuthoritativeExecutionStatus` is signed by the execution signer, binds a fresh query nonce and monotonic status sequence, and describes database fence, attempt, reconciliation, and terminal state. Its exact schema contains literal false authority flags and cannot be decoded as action authority. After a consumed fence, a crash/no-result status can remain uncertain using database-authored evidence, and later provider reconciliation can establish success using response and evidence digests without inventing a device result. Absence or ambiguity remains uncertain and cannot become a safe retry or definitive provider failure.

Every decoder rejects missing, extra, accessor-backed, type-confused, and noncanonical input. Every artifact has a separate domain-separated, length-prefixed transcript; digests are lowercase SHA-256; P-256 SPKI and unpadded base64url IEEE-P1363 signatures are canonicalized. All v2-owned signatures enforce low-S. The imported v1 no-money certificate remains verified by its v1 verifier and accepts its historically valid high-S form, avoiding an incompatible rule change to the live v1 signer. PostgreSQL-backed decimal identifiers are bounded to their actual `bigint` or `integer` domains. Public verification helpers validate the complete no-money-certificate → execution-enrollment → assignment → authority/result/status chain, expected local device/account identity, trusted wall-clock time, and monotonic round-trip bounds where relevant.

Callers must obtain `trustedNow` from a trusted wall-clock source and measure `roundTrip` with a monotonic clock. `verifySignedOneUseActionAuthorityCryptographically` returns authentication evidence with literal `grantsActionAuthority: false`, a replay identity, and a conservative monotonic deadline measured from the original request start so RTT is already spent. The legacy boolean `verifySignedOneUseActionAuthority` is a fail-closed compatibility shim and always returns false.

Cryptographic verification is never consumption. Before an eventual runtime could act, it must atomically check and persist the replay transition in rollback-resistant storage, then call `recheckOneUseActionAuthorityDeadlineAfterAtomicConsumption` immediately before the provider boundary with the matching external receipt and fresh trusted clocks. A successful recheck consumes that branded verification object in-process, so it cannot succeed twice even with a newly constructed matching receipt. This is defense in depth only: the database must still enforce durable idempotency and the execution bridge must still enforce one provider dispatch. The storage-free package cannot prove the external receipt is durable and never grants action authority by itself. Replay-state input is mandatory and omission fails closed for every replay-sensitive verifier.

New assignments and action-authority authentication require a currently valid certificate and execution enrollment. Device results and fresh, nonce-bound, literal-non-authorizing database statuses instead authenticate their signed chain historically, so expiry after a fence cannot strand delayed result handoff or reconciliation. Where an action started, the signed interval from `finalActionStartedAt` to `reportedAt` remains bounded even when transport or ingestion happens much later. Historical verification does not revive action authority.

`playerIdDigest` is a deterministic integrity binding, not a confidentiality or pseudonymization mechanism. Low-entropy Player IDs are dictionary-enumerable from this value. It must stay inside a strict trusted boundary and out of logs, telemetry, support exports, and analytics; any wider exposure requires a separately versioned keyed digest such as HMAC.

## Intentionally absent

This package contains no application import, runtime bridge, provider client, network call, database role or migration, raw lease/authorization token, route, secret, manifest, feature switch, activation writer, or money-action implementation. No execution enrollment or signing key is provisioned. Before any enabled lane could exist, a separate security-reviewed change would need an online transactional database fence, atomic reconciliation ingestion, key enrollment/rotation/revocation, secure Windows key/storage handling, provider-specific execution safeguards, deployment controls, and explicit operator activation. Until all of that exists and is separately approved, these contracts authorize nothing.
